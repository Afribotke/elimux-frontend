### `scholarship_providers`
id, name, slug, logo_url, website, description, email, phone, verified (bool),
status (default 'active'), created_at, updated_at, **is_partner** (bool, default
false), **claimed_by** (uuid), **claimed_at** (timestamptz).
No FK *from* this table to anything. **0 rows** as of this session. Two separate
FKs point *into* it from `scholarships` (`provider_id` and `scholarship_provider_id`
- see §12). RLS: `Providers visible to all` (public SELECT, `true`), `Providers
manageable by admins` (ALL, admin/super_admin via `user_roles`).

### `scholarship_sponsors`
id, name, type, logo_url, website, country_code, contact_email, contact_phone,
description, is_verified (bool), tier (default 'free'), created_by, created_at,
updated_at. No `is_partner`/`claimed_by`/`claimed_at` - that's a `scholarship_providers`-only
concept. RLS: `Public read verified sponsors` (SELECT), `Admins manage sponsors` (ALL).

### `scholarship_applications`
id, **student_id** (uuid, NOT NULL, **no FK constraint** - matches `student_profiles.user_id`
in practice but nothing enforces it), scholarship_id (uuid, NOT NULL, FK →
`scholarships.id`), status (text, default 'draft'; values used in code: draft,
submitted, under_review, awarded, rejected, withdrawn), documents_uploaded (jsonb,
default `[]`), missing_documents (jsonb, default `[]`), ai_match_score (int),
ai_guidance (text), deadline_reminder_sent (bool, default false), reminder_dates
(jsonb, default `[]` - array of `{window, sent_at}`), notes (text), created_at,
updated_at, applicant_id (uuid, nullable, **unused** - `student_id` is the column
actually read/written everywhere), personal_statement, answers (jsonb), documents
(jsonb), current_institution, current_level, field_of_study, gpa (text), review_score
(int), review_notes (text), reviewed_by (uuid), reviewed_at, submitted_at.
RLS: `Students own applications` (ALL), `Users insert own applications` (INSERT),
`Users update own draft applications` (UPDATE), `Admins manage applications` (ALL),
`Admins review applications` (UPDATE), `Applications visible to applicant or
scholarship admin` (SELECT).

### `scholarship_messages`
id, scholarship_id (FK → scholarships.id), sender_id, sender_type, recipient_id,

### `scholarship_profiles`
id, user_id (NOT NULL), gpa, course_field, study_level, year_of_study, county,
country_code (default 'KE'), gender, age, financial_need, orphan_status, disability,
work_experience_years, career_goals, extracurriculars (array), languages (array),

id, user_id, full_name, email, phone, registration_number, university_name,
course_name, course_category, year_of_study (default 1), preferred_locations,

### `user_roles`
id, user_id, role (text, NOT NULL - values seen in code: admin, super_admin),
created_at. RLS: `Users can view own role` (SELECT, authenticated only). No admin-write
policy visible - role assignment happens via service-role key from the backend, not
through RLS-gated client writes.

### `admin_users`
id, email, role (varchar, default 'editor'), is_active (default true), last_login,
created_at. **No RLS policies found on this table at all** - access is service-role
only (bypasses RLS), matches `adminAuth`/`adminMiddleware` reading `x-admin-key`
server-side rather than going through Supabase auth.

## 4. Backend - Auth

`src/middleware/auth.ts`: `adminAuth` (async, checks something beyond the header -
verify before assuming it's identical to `adminMiddleware`), `authMiddleware`,
`adminMiddleware` (sync, checks `req.headers['x-admin-key'] === process.env.ADMIN_KEY`,
403 on mismatch).

`src/middleware/rbac.ts`: `UserRole = "student" | "partner" | "advertiser" |
"institution" | "admin" | "super_admin"`, `AuthenticatedRequest`,
`authenticateToken`, `requireRole(...roles)`, `requireAdmin`, `requireSuperAdmin`.

`src/middleware/user-auth.ts`: `UserAuthRequest`, `requireUser` - used by
`scholarship-applications.ts` and `scholarship-matching.ts`.

`src/middleware/institution-auth.ts`, `employer-auth.ts`, `advertiser-auth.ts`:
domain-specific auth for those portals (`institutionAuth`, `employerAuth` +
`requireEmployerManage`, `advertiserAuth` + `optionalAuth`).

`src/routes/auth.ts` (mounted `/api/auth`): `GET /me` (public), `GET /users`
(`adminAuth`), `PATCH /users/:id/role` (`adminAuth`), `PATCH /users/:id/status`
(`adminAuth`), `DELETE /users/:id` (`adminAuth`). Note this uses `adminAuth`, not
`adminMiddleware` - two different admin-check functions exist in the same file;
verify which one is actually in effect here before assuming X-Admin-Key alone
gates these.

`src/lib/supabase.ts`: exports `supabase` (service-role client), `supabaseKeyRole`,
`supabaseConfigOk` - has a startup guard that logs loudly (not throws) if
`SUPABASE_SERVICE_ROLE_KEY` isn't actually a service_role key.

Frontend `src/context/AuthContext.tsx`: `AuthProvider`, `useAuthContext()` returning
`{ user, session, loading, isAuthenticated, signIn, signUp, signOut, refreshUser }`.
Mounted once in root `layout.tsx`, wraps the whole app.

Frontend `src/hooks/useAuth.ts`: one line -
`export { useAuthContext as useAuth } from '@/context/AuthContext'`. A real, valid
alias - but used in exactly one place (`DesktopNav.tsx`). Everything else imports
`useAuthContext` directly from `@/context/AuthContext`. **`useAuth` is not exported
from `@/context/AuthContext` itself** - only from this hooks/useAuth.ts re-export.

Frontend `src/lib/supabase/client.ts`: `createClient()` - memoized module-level
singleton (`browserClient`), not a new client per call. Has a documented history:
switching `AuthContext` to use this same singleton (instead of a separate plain
`@supabase/supabase-js` client) fixed a "Multiple GoTrueClient instances" bug that
caused `getSession()` to intermittently miss valid sessions.

**Known hazard** (found + fixed twice this session): calling
`supabase.auth.getSession()` directly in a component, concurrently with
`AuthProvider`'s own `getSession()` call on app mount, can deadlock via the Web
Locks API (`lock:sb-<project>-auth-token`) - confirmed live via
`navigator.locks.query()` showing one held + multiple pending requests that never
clear. Fix pattern used everywhere now: consume `useAuthContext()`'s already-resolved
`session`/`loading`, never call `getSession()` a second time in a page/component.

## 9. Known Anomalies / Dead or Duplicated Code

1. **`scholarships.scholarship_provider_id` is a dangling column.** It has a real
   FK to `scholarship_providers.id`, but **no code in either repo references it** -
   confirmed via `git grep` across both repos at HEAD. Nobody knows how it got
   there; it appeared on the live DB between two schema queries in the same session,
   with no corresponding commit in either repo's history. `scholarships.provider_id`
   is the column actually used by the partner-gate feature (its FK was repointed
   from `scholarship_sponsors` to `scholarship_providers` today, since it had 0
   populated rows and the name obviously implied the wrong original target).
   PostgREST embeds referencing `scholarship_providers` from `scholarships` must
   use the explicit hint `scholarship_providers!scholarships_provider_id_fkey` to
   disambiguate between the two FKs, or the query 400s.

2. **`admin-scholarships.ts`'s `POST /` is unreachable dead code.** `admin.ts` is
   mounted at `/api/admin` *before* `admin-scholarships.ts` is mounted at
   `/api/admin/scholarships` (index.ts lines 102 vs 122), and `admin.ts` itself
   defines `POST /scholarships` - same final URL, same method. Express resolves to
   `admin.ts`'s handler every time; `admin-scholarships.ts`'s `POST /` handler body
   never runs. Frontend's `createScholarship()` in `lib/api.ts` hits
   `POST /api/admin/scholarships` and is therefore actually served by `admin.ts`,
   not by the code in `admin-scholarships.ts` that looks like it should own scholarship
   creation. `PATCH /scholarships/:id` (in `admin.ts`) and `PUT /:id` (in
   `admin-scholarships.ts`) don't collide - different HTTP methods on the same path
   template, both reachable.

3. **Two admin-auth functions coexist**: `adminAuth` (`middleware/auth.ts`, used by
   `routes/auth.ts`) and `adminMiddleware` (`middleware/auth.ts`, used by nearly
   everything else). Not confirmed identical - `adminAuth` is `async` and does more
   than the header string-compare `adminMiddleware` does. Worth checking before
   assuming both enforce the same thing.

4. **`useAuth` naming collision risk**: `hooks/useAuth.ts` re-exports
   `useAuthContext` as `useAuth`, used in exactly one component. A brief or draft
   that imports `useAuth` from `@/context/AuthContext` directly (not
   `@/hooks/useAuth`) will fail to compile - that import doesn't exist there, only
   `useAuthContext` and `AuthProvider` do.

5. **`lib/email.ts` naming collision risk**: `applicationApprovedEmailHtml` /
   `applicationApprovedEmailSubject` (and the `...Rejected...` pair) exist, but
   they're for **institution program applications** (`institutionName` param),
   not scholarship applications. The scholarship-application award/reject
   equivalents are named differently: `scholarshipAwardedEmailHtml` /
   `scholarshipAwardedEmailSubject`, `scholarshipRejectedEmailHtml` /
   `scholarshipRejectedEmailSubject`. Near-identical names, different domains,
   different parameters - easy to grab the wrong one.

6. **Document/file uploads have no offline queue path.** `pwaQueue.ts`'s
   `QueueableActionType` has no document/file variant, and its local fallback
   buffer is `localStorage`-based (not IndexedDB) - a base64-encoded file upload
   (uploads elsewhere in the app are capped at 5MB) would risk exceeding typical
   localStorage quota if queued the same way as favorites/reviews. Not built, and
   would need a different storage mechanism if it is.

7. **Reminder logic was duplicated before today** (now fixed): the cron-trigger
   route and the admin-trigger route both now call the single
   `sendScholarshipDeadlineReminders()` in `lib/scholarshipReminders.ts`, rather
   than maintaining two independent copies of the windows/dedup/email logic.

8. **Cleaned up this session, no longer present**: a stray file containing the
   (now-rotated) production `ADMIN_KEY` in plaintext, sitting in the
   `elimux-backend` repo root from a mangled path in an unrelated prior session;
   a stale `layout.tsx.backup.2` in `elimux-frontend`. Both deleted, neither was
   ever committed to git history.
