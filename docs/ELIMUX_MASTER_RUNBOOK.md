## 1. PROJECT OVERVIEW

**ElimuX** is a global education discovery SaaS platform with two core pillars:

- **Course Discovery** — AI-powered search for scholarships, programs, institutions
- **Internship & Attachment** — University students (pre-graduation) and graduates (post-graduation)

Revenue features (partner ads, sponsorships) are secondary to core pillars.

**Stack:**
- Frontend: Next.js 15 (App Router), TypeScript, Tailwind CSS, deployed on Vercel
- Backend: Express.js, TypeScript, deployed on Railway
- Database: Supabase (PostgreSQL + PostgREST)
- Payments: M-Pesa (Daraja API) + Stripe + Paystack
- AI: Multiple providers (Anthropic, OpenAI, DeepSeek, Together, Kimi)
- PWA: Service Worker with offline caching

**Repos:**
- `elimux-frontend` — Next.js app
- `elimux-backend` — Express API
- `elimux-sql` — Database migrations (flat files, no `migrations/` subfolder — see §3, §11.3)
- `elimux-phases-23` — Project documentation

## 5. AUTHENTICATION & AUTHORIZATION

### 5.1 Auth Middleware

| Middleware | Location | Type | Used By |
|---|---|---|---|
| requireUser | middleware/user-auth.ts | Async | scholarship-applications, scholarship-matching |
| **adminAuth** | middleware/auth.ts | Async | **All admin-gated routes** (unified onto this single function in Cycle 005 — previously split between this and `adminMiddleware`, which is now deleted) |
| authenticateToken | middleware/rbac.ts | Async | RBAC system |
| requireRole | middleware/rbac.ts | Async | Role-specific routes |
| institutionAuth | middleware/institution-auth.ts | Async | Institution portal |
| employerAuth | middleware/employer-auth.ts | Async | Employer portal |
| advertiserAuth | middleware/advertiser-auth.ts | Async | Advertiser portal |

**`adminAuth` checks:** EITHER the shared `x-admin-key` header matching `process.env.ADMIN_KEY` (checked first, short-circuits immediately), OR a Bearer Supabase JWT belonging to a user whose role — read from `admin_users` (by email), then `user_roles` (by user_id), then `user_metadata.role` — is `admin` or `super_admin`. The JWT path is race-timed against an 8s timeout. Returns 401 on any failure.

> **Correction from the Kimi draft**: the original had a row for
> `adminMiddleware` here ("Sync / Most admin routes") and a SECURITY NOTE
> saying the two functions "are NOT confirmed identical" with resolution
> "documented in Cycle 003." Both are now obsolete — Cycle 003 documented the
> difference (JSDoc + a security note in the code), and Cycle 004... no,
> correction: it was actually **Cycle 004** that added the JSDoc/security
> note, and **Cycle 005** that acted on the finding by unifying everything
> onto `adminAuth` and deleting `adminMiddleware` entirely. It no longer
> exists in the codebase, so it's removed from this table rather than shown
> as a still-active, still-differing function.

### 5.2 Frontend Auth

**Context:** `src/context/AuthContext.tsx`
- Exports: `AuthProvider`, `useAuthContext()`
- Returns: `{ user, session, loading, isAuthenticated, signIn, signUp, signOut, refreshUser }`
- Singleton client: `src/lib/supabase/client.ts` (memoized, prevents a Web Locks deadlock)

**CRITICAL:** Never call `supabase.auth.getSession()` directly in a component. Always consume `useAuthContext()`. Direct calls raced against `AuthProvider`'s own `getSession()` call have caused a confirmed, live-reproduced deadlock via the Web Locks API (`navigator.locks.query()` showed one held + multiple pending requests that never cleared) — found and fixed twice this session on `/applications` pages that called `getSession()` directly instead of consuming the context.

**Hook alias:** `src/hooks/useAuth.ts` re-exports `useAuthContext` as `useAuth`. Used only in `DesktopNav.tsx`. Everywhere else imports `useAuthContext` directly. Importing `useAuth` from `@/context/AuthContext` itself doesn't work — that module doesn't export a name by that spelling, only `useAuthContext` and `AuthProvider`.

### 5.3 Admin Key Flow

1. Admin logs in → frontend stores admin key in `AdminKeyContext`
2. Admin pages read the key from context
3. `lib/api.ts` passes it as the 3rd arg to `request()`, which sets the `x-admin-key` header
4. Backend `adminAuth` validates the header against `process.env.ADMIN_KEY`

> **Correction from the Kimi draft**: step 4 said "Backend adminMiddleware
> validates header" — updated to `adminAuth` per Cycle 005.

## 7. PWA / OFFLINE STATUS

### 7.1 Service Worker (`public/sw.js`)

- **Static cache:** `elimux-static-v4` — cache-first for same-origin assets
- **API cache:** `elimux-api-v4` — network-first for most GETs
- **Scholarship cache:** stale-while-revalidate for `/api/scholarships*`
- **Excluded:** `/api/scholarship-applications*` stays network-first — deliberately, since showing a stale application status before a background refresh quietly updates it is misleading in a way a scholarship listing being a few hours stale isn't

### 7.2 Pre-cached Shell Pages

- `/` (home)
- `/scholarships/`
- `/applications/`

### 7.3 Background Sync

- Hook: `useBackgroundSync()` — mount exactly once, via `BackgroundSyncManager.tsx`
- Queueable actions: `favorite`, `review`, `application` (program applications only — see limitation below)
- Storage: `localStorage` (`elimux-local-pending-actions`), **not** IndexedDB
- **Limitation:** no document/file upload queue exists. Uploads elsewhere in the app are capped at 5MB; base64-encoding a file that size for localStorage risks exceeding typical quota, so this wasn't built as a simple extension of the existing queue.

### 7.4 Offline Indicator

- Component: `OfflineIndicator.tsx`
- Existed since the original PWA commit but was never rendered anywhere in the app. Wired into root `layout.tsx` on 2026-08-16.

## 12. EMERGENCY PROCEDURES

### 12.1 Rollback a Bad Cycle

```bash
# Find the cycle number in audit-log.md
cp docs/archive/bridge-YYY.md docs/bridge.md
git add docs/bridge.md
git commit -m "rollback: restored bridge.md to cycle-YYY"
```

### 12.2 Rotate a Leaked Secret

1. Generate a new key in the provider dashboard (Stripe, Supabase, etc.)
2. Update it in Railway/Vercel environment variables
3. Delete the old key from the provider dashboard
4. Check git history: `git log -p | grep OLD_KEY`
5. If it was ever committed, rotate immediately regardless and consider a history rewrite

### 12.3 Database Emergency

- PITR restore: Supabase Dashboard → Database → Backups → Point in Time Recovery
- Manual rollback: run the inverse migration from `elimux-sql/`
- Contact Supabase support for unrecoverable issues

### 12.4 API Down

- Check the Railway dashboard for service status
- Check the Supabase dashboard for DB connectivity
- Verify environment variables are set (especially `SUPABASE_SERVICE_ROLE_KEY`)
- Check recent commits for breaking changes
